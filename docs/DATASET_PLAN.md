# 総務省選挙データセット全体構想

## 1. 目的

総務省が公表する国政選挙の資料を、原資料へ戻れる状態を保ちながら、選挙回を横断してSQLで分析できるデータセットにする。

当面の実装対象は衆議院議員総選挙・最高裁判所裁判官国民審査（`shugiin`）である。参議院議員通常選挙（`sangiin`）は同一リポジトリ・同一warehouse方針で後続拡張する（詳細は「9. 参議院への拡張方針」）。

本プロジェクトでは、推測による補完より再現性を優先する。未正規化資料は欠損値として混ぜず、`raw_only` として明示する。

## 2. データの三層

1. **Raw** — 総務省のExcel/PDF原本、セル・ページを保持したraw JSON、URL、SHA-256。
2. **Normalized** — 資料固有の表を、`contest`、`metric`、`value` など共通のlong形式へ変換。すべての値に出典ファイル・シート・セルまたはページを持たせる。
3. **Warehouse** — 全選挙回を統合したDuckDBとParquet。選挙、出典、fact、カバレッジ、検証結果を分離する。

RawとNormalizedは監査・再処理用、Warehouseは分析・配布用である。

## 3. Warehouse v1

### `elections`

選挙回、選挙種別（chamber）、投票日。主キーは `election_id`（例: `shugiin-51`、将来 `sangiin-27`）。
`election_type` / chamber は `shugiin` または `sangiin` を取る。

### `source_documents`

出典資料。選挙回、資料番号、URL、原ファイル名、データセット名を保持する。

### `facts`

分析値の主表。1行は1つの測定値で、選挙回、選挙種別、都道府県、比例ブロック、政党、裁判官、性別、年齢階級、指標、値、単位と出典座標を持つ。都道府県にはJIS都道府県コードを付ける。

### `normalization_coverage`

資料番号ごとの `normalized` / `raw_only` と生成件数。取得済みと正規化済みを区別する。

### `validation_results`

機械検証の結果。v1では主キー重複、出典参照、国民審査、有効・無効票、男女計、有権者・投票者・棄権者の算術整合を検査する。後続版で候補者得票と全国計の検算を追加する。

## 4. ID方針

- factと出典には、内容・出典座標から決定的に生成するIDを使う。
- 候補者は当面「その選挙における立候補」を単位にする。
- 空白除去済み氏名だけで同一人物を断定しない。
- 政党名は原表記を保持し、時系列別名テーブルを別途作る。
- 市区町村は全国地方公共団体コードと有効期間を導入する。合併前の自治体を現在の自治体へ黙って置換しない。

## 5. 配布形式

- `soumu_election.duckdb`: ローカルSQL分析用の単一ファイル。
- `parquet/*.parquet`: Python、R、BIツール、クラウドDWH向け。
- JSON: raw・normalized層およびAPI出力用。
- CSVは利用者向けエクスポートに限定する。

## 6. 品質原則

- 原表の文字列と正規化値を分離する。
- すべてのfactから原資料のURLと座標へ遡れるようにする。
- 算術不整合の行は無条件に採用しない。
- PDFは表構造と合計値を検証できた資料だけsemantic変換する。
- スキーマ、生成日時、入力選挙回、件数をwarehouse manifestへ記録する。

## 9. 参議院への拡張方針

最終更新: 2026-08-08

### 9.1 結論（リポジトリ構成）

**別リポジトリ（`soumu-shugiin` / `soumu-sangiin` の分割）は採用しない。**  
現行の `soumu-election` を一本化し、衆院・参院を chamber で分ける。

理由:

- 取得・raw JSON・manifest・warehouse・Pages検索UIの骨格は共通化できる。
- 空白除去・ページ送り・検証・デプロイを二重メンテするとコストが大きい。
- リポジトリ名はもともと選挙横断を想定できる `soumu-election` である。
- warehouse はすでに `election_id = shugiin-{回}`、選挙種別 `"shugiin"` を持つ前提がある。

「コードだけ割る」の解釈:

- ○ 共通処理は `soumu_election/` に残し、衆院／参院固有パーサだけ分ける。
- × リポジトリごとコピーして別運用する。

別リポが妥当になるのは、公開主体・運用・Pagesデプロイを完全分離したい場合に限る。その場合でも、最初から2リポではなく共通パッケージ＋個別フロントの方がよい。

### 9.2 衆院と参院で共通／固有になるもの

| 層 | 方針 |
|---|---|
| データ配置 | `data/sangiin{回}/`、`config/sangiin{回}.json` を衆院と同じ型で追加 |
| ID | `election_id = sangiin-{回}`、`election_type` / chamber = `sangiin` |
| 共通コード | ダウンロード、raw JSON、warehouse生成、DuckDB-Wasm UI骨格 |
| 固有コード | 参院の資料項番・表形式・contest（選挙区／比例、改選など）に対応するパーサ |
| UI | 同一サイトで chamber タブまたはフィルタ。必要ならパス分割 |
| リポ分割 | しない（少なくとも初期〜中期） |

制度・原本の差分（選挙区の意味、比例の単位、改選、資料レイアウト）があるため、**パーサの安易な共用はしない**。スキーマと運用だけ揃える。

### 9.3 ディレクトリ案

```text
config/
  shugiin44.json … shugiin51.json   # 既存
  sangiinXX.json                    # 追加（回次は総務省の回に合わせる）
data/
  shugiin44/ … shugiin51/           # 既存
  sangiinXX/
    raw/
    raw_json/
    normalized/
    manifest.json
src/soumu_election/
  download.py / normalize.py / warehouse.py   # chamber対応へ拡張
  parsers_shugiin/ …                          # 既存衆院寄り処理（必要なら整理）
  parsers_sangiin/ …                          # 参院固有パーサ
web/
  # chamber フィルタまたは衆院/参院タブ
```

### 9.4 実装ステップ

1. **調査**: 参院1回分について、総務省indexの項番・Excel/PDF形式・衆院資料との対応表を作る。
2. **設定**: `config/sangiinXX.json` と `data/sangiinXX/` の試作パイプライン（raw → raw_json）。
3. **スキーマ固定**: warehouse の `elections.election_type`（chamber）と `election_id` 規約を正式化する。衆院既存データは `shugiin` のまま互換維持。
4. **正規化**: 得票・投票率など優先度の高い資料から semantic 変換。未検証は `raw_only`。
5. **UI**: 検索条件に chamber を追加し、衆院UIを壊さない。
6. **公開**: 参院のカバレッジと検証が安定してから Pages に載せる。

### 9.5 品質・非目標

- 衆院factと参院factを黙って同一contest語彙に潰さない。必要な語彙差分は明示する。
- 人物・政党の名寄せは衆院と同様、後段テーブルで行い raw を上書きしない。
- 初期リリースで衆院と参院の全市区町村・全資料を同時完璧にしない。1回・主要資料から積み上げる。

### 9.6 判断の見直し条件

次のいずれかに該当したら、配布単位（別Pages・別warehouseファイル・最悪別リポ）を再検討する。

- データ量やビルド時間が運用上分離必須になった場合
- 公開範囲・ライセンス・メンテナを厳密に分けたい場合
- 参院だけ別サイトとして独立ブランド運用したい場合

### 9.7 表示表記（UI）

画面・CSVの人間可読ラベルは、回次だけでは衆院・参院が衝突しうるため次の形式とする。

- 衆院: `2026-衆51回`（`{投票年}-衆{回}回`）
- 参院: `YYYY-参N回`（取込後に同じ規則）

機械用キーは従来どおり `election_id`（`shugiin-51` / `sangiin-N`）と `election_kaiji` を用いる。
