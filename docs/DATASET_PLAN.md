# 総務省・衆議院選挙データセット全体構想

## 1. 目的

総務省が公表する衆議院議員総選挙・最高裁判所裁判官国民審査の資料を、原資料へ戻れる状態を保ちながら、選挙回を横断してSQLで分析できるデータセットにする。

本プロジェクトでは、推測による補完より再現性を優先する。未正規化資料は欠損値として混ぜず、`raw_only` として明示する。

## 2. データの三層

1. **Raw** — 総務省のExcel/PDF原本、セル・ページを保持したraw JSON、URL、SHA-256。
2. **Normalized** — 資料固有の表を、`contest`、`metric`、`value` など共通のlong形式へ変換。すべての値に出典ファイル・シート・セルまたはページを持たせる。
3. **Warehouse** — 全選挙回を統合したDuckDBとParquet。選挙、出典、fact、カバレッジ、検証結果を分離する。

RawとNormalizedは監査・再処理用、Warehouseは分析・配布用である。

## 3. Warehouse v1

### `elections`

選挙回、選挙種別、投票日。主キーは `election_id`（例: `shugiin-51`）。

### `source_documents`

出典資料。選挙回、資料番号、URL、原ファイル名、データセット名を保持する。

### `facts`

分析値の主表。1行は1つの測定値で、選挙回、選挙種別、都道府県、比例ブロック、政党、裁判官、性別、年齢階級、指標、値、単位と出典座標を持つ。都道府県にはJIS都道府県コードを付ける。

### `normalization_coverage`

資料番号ごとの `normalized` / `raw_only` と生成件数。取得済みと正規化済みを区別する。

### `validation_results`

機械検証の結果。v1では主キー重複、出典参照、国民審査、有効・無効票、男女計、有権者・投票者・棄権者の算術整合を検査する。後続版で候補者得票と全国計の検算を追加する。

## 4. ID方針

- factと出典には、内容・出典座標から決定的に生成するIDを使う。
- 候補者は当面「その選挙における立候補」を単位にする。
- 空白除去済み氏名だけで同一人物を断定しない。
- 政党名は原表記を保持し、時系列別名テーブルを別途作る。
- 市区町村は全国地方公共団体コードと有効期間を導入する。合併前の自治体を現在の自治体へ黙って置換しない。

## 5. 配布形式

- `soumu_election.duckdb`: ローカルSQL分析用の単一ファイル。
- `parquet/*.parquet`: Python、R、BIツール、クラウドDWH向け。
- JSON: raw・normalized層およびAPI出力用。
- CSVは利用者向けエクスポートに限定する。

## 6. 品質原則

- 原表の文字列と正規化値を分離する。
- すべてのfactから原資料のURLと座標へ遡れるようにする。
- 算術不整合の行は無条件に採用しない。
- PDFは表構造と合計値を検証できた資料だけsemantic変換する。
- スキーマ、生成日時、入力選挙回、件数をwarehouse manifestへ記録する。

## 7. 実装ロードマップ

### Phase 1（今回）

- 第44～51回の既存normalized JSONを統合
- DuckDB・Parquet生成
- 都道府県コード、出典表、カバレッジ表、検証表
- 再生成可能なCLIと利用例

### Phase 2

- 第44回PDFの残資料を正規化
- 候補者別・市区町村別得票を専用テーブル化
- 投票関連の横断的な算術検証を拡充

### Phase 3

- 自治体コードと合併履歴
- 政党別名・改称・合併履歴
- `candidacies` と候補者人物同定（確信度・根拠付き）

### Phase 4

- さらに古いデジタル公開回へ拡張
- PostgreSQL/APIへの展開
- データ辞書、リリース番号、差分更新

## 8. 完了条件

同じ入力から同じ主キー・件数でDBを再生成でき、各factの出典を追跡でき、未正規化範囲と検証失敗をSQLで確認できることを、各リリースの最低条件とする。
